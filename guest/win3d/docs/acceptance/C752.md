# C752. The submit escape checked a size that wraps

Finding F4 of the win3d driver review
([the review](../../../../docs/reviews/win3d-driver.md), card #741). The
`VIOGPU_SUBMIT_CMD` escape of the kernel driver takes a command size from
the calling program. It added that size to the 12 bytes of the request
header in 32 bits and compared the sum with the payload length. A size of
`0xFFFFFFF4` or more wraps the sum to less than 12, so the check passed. The
driver then asked for that many bytes of nonpaged pool and copied that many
bytes out of the escape buffer.
[Fix](../../patches/kmd/kmd-check-submit-escape-size.patch): the check
subtracts, and the escape returns `STATUS_INVALID_BUFFER_SIZE`.

The review's claim is confirmed: a standard user bugchecks the guest with
one call.

## Host test

`scripts/test_kmd_submit_bounds.py` takes the header with the check out of
the patch and compiles `tests/kmd/submit_bounds_test.cpp` against it. Built
with `-DOLD_DRIVER` the same program runs on the expression the driver had
before. `win3d-check` of `just ci::check` runs it.

| Check | Before the patch | With the patch |
| --- | --- | --- |
| A command that fits, one byte too long, a payload shorter than the header (8 checks) | pass | pass |
| `CmdSize` `0xFFFFFFF8`, `0xFFFFFFF4` and `0xFFFFFFFF` with a payload of 12 bytes | **accepted** | refused |
| `CmdSize` `0xFFFFFFF4` with a payload of 65535 bytes | **accepted** | refused |
| `CmdSize` `0xFFFFFFF3`, the last that does not wrap | refused | refused |
| For every payload length from 0 to 65535, an accepted command ends inside the payload | **fails** | pass |

## Guest proof

`probes/submit/submit_probe.c` opens the virtio-gpu adapter, makes a device,
makes its host context with `VIOGPU_CTX_INIT` and sends one
`VIOGPU_SUBMIT_CMD` request. `tests/kmd/submit-probe.sh` makes a local user
that is a member of Users only, runs one case per process as that user, and
reads the bugcheck records of the System log after each case. The private
data is 68 bytes in every case: the 40 bytes of `VIOGPU_ESCAPE`, the 12-byte
header and 16 command bytes.

The driver checks the sizes first and the command type after them. Command
type 0 is refused after the size check and nothing is allocated or sent. So
the status of a case with type 0 says what the size check did, without a
risk for the guest.

One lab for both runs: a clone of `windows-11@26100.1742.11#win3d` with
16 GiB of memory on AMD1 (`0000:72:00.0`), vmlab-hv, Venus. The capsets of
the adapter were 1, 2 and 4, and the context used capset 1. "Before" is the
driver of the variant, `100.6.101.58116`, the series without this patch.
"After" is the package of this card installed over it, driver
`100.6.101.58117`.

| Case | `DataLength` | `CmdType` | `CmdSize` | Before (58116) | After (58117) |
| --- | --- | --- | --- | --- | --- |
| `fits` | 28 | 0 | 16 | `0xc000000d` `STATUS_INVALID_PARAMETER` | the same |
| `too-long` | 28 | 0 | 17 | `0xc0000206` `STATUS_INVALID_BUFFER_SIZE` | the same |
| `wrap-type0` | 12 | 0 | `0xFFFFFFF8` | `0xc000000d`: **the size check passed** | `0xc0000206` |
| `wrap-first` | 12 | 1 | `0xFFFFFFF4` | **bugcheck `0x50`**, the escape did not return | `0xc0000206` |
| `wrap` | 12 | 1 | `0xFFFFFFF8` | **the guest went down**, the escape did not return | `0xc0000206` |

Before: 2 of 5 cases pass. After: 5 of 5 pass, and the System log has no new
bugcheck record.

The record of `wrap-first` before the fix:

```
The computer has rebooted from a bugcheck. The bugcheck was: 0x00000050
(0xffffa4803f5e3000, 0x0000000000000000, 0xfffff80462fd2944,
0x0000000000000002). A dump was saved in: C:\WINDOWS\Minidump\112326-2546-01.dmp.
```

`0x50` is `PAGE_FAULT_IN_NONPAGED_AREA`. The second parameter says a read,
and the address is the start of a page: the copy read past the end of the
mapped escape buffer. The allocation of about 4 GiB of nonpaged pool
succeeded on this guest.

`wrap` ran 4 seconds after the guest was back from that bugcheck. The agent
channel closed during the call, and the guest came up at the Windows
recovery screen ("It looks like Windows didn't load correctly"), which
Windows shows after two failed starts in a row. It needed a key press on the
console to start Windows again. No bugcheck record of this second crash was
in the System log afterwards, and the record of the first one was gone from
it too. The record above was read between the two crashes. So for `wrap`
the evidence is the lost guest, not a stop code.

## End-to-end run

`tests/e2e/run.sh --template windows-11 --host-gpu AMD1` at commit
`93cf714d`, on a fresh clone of `windows-11@26100.1742.11`, with the package
built from that commit and installed by the documented command. The guest
ran driver `100.6.101.58117`.

**PASS: 12 of 12 Done checks**, and the 8 extra rows pass too. The six
probes of the Done items rendered at 46 to 60 fps with a correct readback.
The run held AMD1 for 865 s. No Xid was logged on the host before or after
any of the three holds of this card.

The probe source changed once after these runs: two status macros were
renamed to stop a compiler warning. The values are the same.

## Not changed

- `CmdSize` is not checked against a multiple of 4, and the escape does not
  check that the device has a host context of a capset that takes the
  command. The host parses the command.
- The escape is still open to every process that can open the adapter.
