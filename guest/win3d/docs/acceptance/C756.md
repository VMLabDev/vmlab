# C756. The source of a present copy was mapped in Patch

Finding F8 of the win3d driver review
([the review](../../../../docs/reviews/win3d-driver.md), card #741). In a
Venus context the kernel driver copies a Blt present from a blob into a GDI
surface. It mapped the two surfaces in `DxgkDdiPresent` only when both were
resident. Otherwise it left the mapping to `DxgkDdiPatch`, which cannot
refuse one present. Whether the source blob maps is decided by values that
the calling program writes.
[Fix](../../patches/kmd/kmd-map-present-source-in-present.patch): a blob
source without the mappable flag is refused when the copy is staged, the
source blob is mapped in `Present` in every case, and `Patch` no longer
returns the status of a failed mapping. The driver with the fix is
`100.6.101.58119`.

## What the test found

The review asked the test to decide whether the fault is real. The answer
has two halves.

- **The defect is real.** As a standard user, the driver before the fix
  accepts a present that it cannot carry out: `DxgkDdiPresent` returns
  success for a source blob without the mappable flag that is not resident
  yet, and the DMA buffer is queued with its two patch locations.
- **The bugcheck was not reached.** Windows 11 (10.0.26100) stops that DMA
  buffer before it calls `DxgkDdiPatch`. The trace says "Failing
  preparation since allocation has not been fully committed prior to being
  scheduled. Did user mode forget to schedule a sync packet?". Windows puts
  the device of the program into its error state and `D3DKMTPresent`
  returns `0xC01E0200` (`STATUS_GRAPHICS_GPU_EXCEPTION_ON_DEVICE`). The
  guest stayed up in 14 of 14 runs that ended this way on the old driver.
  No bugcheck record was written in any run of this card.

So the severity "crash" of F8 is not confirmed on this Windows. What kept
the guest up is a check of Windows, not the driver. The fix makes the driver
refuse by itself.

Two routes of the review do not exist:

- A blob that the host refuses to create never becomes an allocation.
  `DxgkDdiOpenAllocation` creates the blob and waits for the host, so
  `D3DKMTCreateAllocation` fails with `0xC0000001` (case `unknown-blob`,
  the same before and after).
- When the source is resident, `Present` gets a nonzero segment for it, and
  the old driver already mapped in `Present` and refused there.

A program must also ask for the residency of its source
(`D3DKMTMakeResident`): the driver reports explicit residency, and Windows
refuses a present of a source that nobody asked for ("Failed to reference
DMA buffer: Allocation is not requested to be resident").

## Host test

`scripts/test_kmd_blt_map.py` takes the header with the two rules out of the
patch and compiles `tests/kmd/blt_map_test.cpp` against it. Built with
`-DOLD_DRIVER` the same program runs on the two expressions the driver had
before. `win3d-check` of `just ci::check` runs it.

| Check | Before the patch | With the patch |
| --- | --- | --- |
| What the user-mode drivers send: a mappable Venus image into a GDI surface, Desktop Duplication, the refusals that existed, both surfaces resident or mapped (10 checks) | pass | pass |
| A blob source with `BlobFlags` 0, or with other flags only, is refused for a GDI destination | **accepted** | refused |
| A source that is not resident is mapped in `Present` | **left to `Patch`** | mapped in `Present` |
| Over all 256 combinations of blob kinds, flags and residency: a staged copy has a mappable blob source, and `Present` maps every blob of it | **fails** | pass |

Before: 10 of 14 checks pass, and the 4 that fail are the F8 checks. With
the patch: 14 of 14. Two more tests read the patch itself: the driver calls
both rules, and the `return status;` of `Patch` after a failed mapping is
gone.

## Guest proof

`probes/present/present_probe.c` does what a windowed Direct3D 9 program
does, with `D3DKMT` calls only. It makes a device, a Venus host context and
a context, one allocation of 256 by 256 pixels whose private data it
writes, and presents it with `Blt` to its own window.
`tests/kmd/present-probe.sh` runs it through `tests/guest/Run-Probe.ps1` in
the desktop session of the autologon user `win3d`, a member of Users only,
and reads the bugcheck records of the System log after each case.

The host must know the blob of a source without the mappable flag. The
probe makes one: four Venus commands through the `VIOGPU_SUBMIT_CMD` escape
(`vkCreateInstance`, `vkEnumeratePhysicalDevices`, `vkCreateDevice`,
`vkAllocateMemory` with dma-buf export) give device memory with a known
object id, and the allocation names that id with `BlobFlags` 0 or 2.

With `--backlog 8` the probe puts eight allocations of 16 MiB on the paging
queue in front of the source and presents at once. The source is then not
resident when `DxgkDdiPresent` runs: the state of the finding.

Two labs on AMD1 (`0000:72:00.0`), vmlab-hv, Venus, 16 GiB of memory, both
clones of `windows-11@26100.1742.11#win3d`. "Before" is the driver of the
variant, `100.6.101.58116`. "After" is the package of this card installed
over it, driver `100.6.101.58119`. One present per case.

| Case | Source | Before (58116) | After (58119) |
| --- | --- | --- | --- |
| `unknown-blob` | Blob id the host does not know | `D3DKMTCreateAllocation` `0xC0000001` | the same |
| `mappable` | Shared memory, mappable | present accepted, `0x00000000` | the same |
| `not-mappable` | Device memory, `BlobFlags` 0, resident | refused, `0xC01E0006` | the same |
| `shareable` | Device memory, `BlobFlags` 2, resident | refused, `0xC01E0006` | the same |
| `mappable --backlog 8` | Mappable, not resident yet | Windows refuses, `0xC01E0200` | the same |
| `not-mappable --backlog 8` | `BlobFlags` 0, not resident yet | **the driver accepts**, Windows stops the buffer, `0xC01E0200` (2 of 2 runs) | the driver refuses, `0xC01E0006` (2 of 2) |
| `shareable --backlog 8` | `BlobFlags` 2, not resident yet | **the driver accepts**, `0xC01E0200` (1 of 2: in the other run the source was resident in time) | the driver refuses, `0xC01E0006` (2 of 2) |

The probe fails a case when Windows had to stop a present that the driver
must refuse. Before: 4 of 4 cases pass without a backlog, and 3 of 5 runs
with a backlog fail. After: 4 of 4 and 5 of 5 pass. The exploration runs
before these gave the same two statuses: `0xC01E0200` in 11 of 11 runs of
`not-mappable` with a backlog on the old driver, `0xC01E0006` in 5 of 5 on
the new one.

`0xC01E0006` is `STATUS_GRAPHICS_PRESENT_OCCLUDED`. It is what
`D3DKMTPresent` returns here when the driver fails `DxgkDdiPresent`.

### What the trace shows

A trace of `Microsoft-Windows-DxgKrnl` (`logman`, all keywords) of the case
`not-mappable --backlog 8`:

| | Before (58116) | After (58119) |
| --- | --- | --- |
| `DxgkDdiPresent` | returns success | "Driver failed Present `0xC00000BB`" |
| DMA buffer | queued, `bPresent=true`, 2 patch locations | none |
| Scheduler | "Failing preparation since allocation has not been fully committed prior to being scheduled", device error reason 18 | not reached |
| `DxgkDdiPatch` | not called | not called |
| `D3DKMTPresent` | `0xC01E0200` | `0xC01E0006` |

The trace of `not-mappable` without a backlog is the same before and after:
"Driver failed Present `0xC00000BB`" (`STATUS_NOT_SUPPORTED`), then
`0xC01E0006`.

### How the probe got its present

The form of the request is not documented, so the probe took it from a
trace of `probes/d3d9`: a window, a source, no destination, and the flags
`0x11001` (`Blt`, `PresentCountValid`, `RedirectedBlt`). Windows makes the
staging surface of the window itself and passes it to `DxgkDdiPresent` as
the destination. The probe creates its source as a resource, as the
user-mode drivers do. Three forms that Windows refuses before the driver:

- A present without a sub-rectangle: `0xC000000D`.
- A destination that the program names (the window surface of
  `DwmpDxGetWindowSharedSurface`): the trace says "destination must be
  primary", `0xC000000D`.
- A source without a residency request: the trace says "Allocation is not
  requested to be resident", `0xC01E0006`.

## End-to-end run

`tests/e2e/run.sh --template windows-11 --host-gpu AMD1` at commit
`7b61882d`, on a fresh clone of `windows-11@26100.1742.11`, with the package
built from that commit and installed by the documented command. The guest
ran driver `100.6.101.58119`.

**PASS: 12 of 12 Done checks**, and the 8 extra rows pass too. The ten
probes rendered at 53 to 60 fps with a correct readback. The two Direct3D 9
probes, whose windowed presents are the Blt presents this patch changes,
ran at 59.2 and 57.8 fps. The run held AMD1 for 1224 s. No Xid was logged
on the host before or after any hold of this card.

The guest proof ran on the driver built at commit `53b92a70`. The patch of
commit `7b61882d` differs from it in comments and in its description only.

## Not changed

- The second half of the patch has no guest test. `Patch` returns success
  when its mapping fails and the copy of that present is skipped. The case
  is a mapping lost between `Present` and `Patch`, by a device reset.
  Nothing in this card could make Windows call `DxgkDdiPatch` in that
  state. `scripts/test_kmd_blt_map.py` checks that the `return status;` is
  gone from the patch.
- Whether Windows answers a failed `DxgkDdiPatch` with bugcheck `0x119` was
  not tested. The statement is from a comment of the upstream source.
- The check that kept the guest up belongs to Windows 11 26100. Windows 10
  was not tested.
- A present that fails this way leaves the device of the calling program in
  its error state. That is the behaviour of Windows for a failed
  `DxgkDdiPresent`, with and without the fix.
