# C757. The helpers' pipe read past its buffer, and CreateAllocation used a failed allocation

Findings F9 and F10 of the win3d driver review
([the review](../../../../docs/reviews/win3d-driver.md), card #741). Two
patches of the kernel driver series fix them:
[`kmd-read-helper-pipe-message-inside-buffer.patch`](../../patches/kmd/kmd-read-helper-pipe-message-inside-buffer.patch)
and
[`kmd-check-create-allocation-memory.patch`](../../patches/kmd/kmd-check-create-allocation-memory.patch).
The driver with both is `100.6.101.58120`.

## F9. The pipe of the two helpers

`vgpusrv.exe`, the service, and `viogpuap.exe`, which the service starts in
the console session, talk over the named pipe `viogpupipe<session>`. Each
keeps a buffer of 1024 `wchar_t`, 2048 bytes.

| | Before | After |
| --- | --- | --- |
| `PipeServer::Read` | Asked `ReadFile` for `DATA_BUFFER_SIZE * sizeof(wchar_t)` bytes. `DATA_BUFFER_SIZE` had no parentheses, so that is 1024 × 2 × 2 = 4096 bytes into 2048 | Both ends read through `VioGpuPipeReadMessage` (`viogpu/shared/pipe_bounds.h`), which counts in bytes and never asks for more than the room left |
| `PipeClient::Read` | Asked for 2048 bytes at `&m_buffer[read]`, where `read` counts bytes and the index counts `wchar_t`: the second piece of a message lands at twice its offset | The same function |
| The string | Neither loop wrote a terminator. A sender ends its text with one byte, half a `wchar_t`. `GetData()` read on until it met a zero | The last `wchar_t` of the buffer stays free and the buffer is zeroed behind the message |
| A message that does not fit | Written past the buffer | Taken off the pipe and dropped. The buffer is then an empty string, which the helpers ignore. The next message is read from its first byte |
| `DATA_BUFFER_SIZE` | `DATA_BUFFER_LENGTH * sizeof(wchar_t)` | In parentheses |

The review's claim for the service is confirmed. Its claim for
`viogpuap.exe` holds only for a handle in message read mode, and
`viogpuap.exe` leaves its handle in byte read mode, where `ReadFile` never
reports a second piece. What `viogpuap.exe` did have is the string without
an end.

### Proof in a guest

[`probes/pipe`](../../probes/README.md#the-pipe-probe) is one program linked
with `viogpu/shared/pipe.cpp` of the driver source, once without the patch
(`pipe_probe_before.exe`) and once with it (`pipe_probe_after.exe`). It
drives the two classes of the helpers on a pipe of its own, with the object's
buffer in front of two guard pages, so it counts what is written past the
buffer. [`tests/kmd/pipe-probe.sh`](../../tests/kmd/pipe-probe.sh) runs it as
a new local account that is a member of Users only.

The runs were on helios on 2026-11-24, in a clone of the Windows 11
`26100.1742.11#win3d` template on vmlab-hv. The lab had no `gpu {}` block:
the probe is all user mode and uses no host GPU.

| Case | Source before the patch | Source with the patch |
| --- | --- | --- |
| `server-command`: the server reads `\CONNECTED` into a buffer that held other data | The string runs through the whole buffer and the guard: 5119 units | `\CONNECTED`, 10 units |
| `server-long`: one message of 3000 bytes to the server, then a command | **952 bytes written past the buffer**, from its first byte on. The command behind it is not read right | Nothing past the buffer, the message is dropped, the command is read |
| `server-full`: a message of 2048 bytes with no zero | The string runs past the buffer | Dropped, the next command is read |
| `service-thread`: `Init()` as the service calls it, the thread reads 3000 bytes into the heap buffer | **The process dies**: exit code 116, the low byte of `0xC0000374` (`STATUS_HEAP_CORRUPTION`). The record on disk stays at `requesting` | `HeapValidate` says the heap is whole |
| `client-command`: the client reads `\CLOSE` | The string runs past the buffer | `\CLOSE`, 6 units |
| `client-long`: 3000 bytes to the client in byte read mode | 2048 bytes fill the buffer, the string runs past it | 2046 bytes, 1023 units, terminated |
| `client-long-message-mode`: the same in message read mode | **952 bytes written past the buffer**, the first of them 2048 bytes behind its end | Nothing past the buffer |
| Result | **fails**: 7 of 7 | **passes**: 7 of 7 |

The two programs differ only in `pipe.cpp`, `pipe.h` and the new header.
Their sha256 are `21e79c25…` (before) and `a5751f84…` (after).

### Who can write to the pipe

The review left open who may write to the pipe of the service. The case
`access` of the probe tried to open `\\.\pipe\viogpupipe1` as the standard
user, in the guest with the service of the installed package running:

| Open for | Result |
| --- | --- |
| Reading and writing | Error 5, access denied |
| Reading | Succeeded when no `viogpuap.exe` was connected (this lab has no GPU device). The second try got error 231, all pipe instances busy |

So a standard user cannot send the service a message through its own pipe.
The overflow in the service was reachable by an administrator, and by a
standard user only where the user's process made the pipe name first, which
was not tried. That a standard user can take the one instance of the pipe by
opening it for reading is a separate fault that this card does not change.

### Proof on the build host

[`tests/kmd/pipe_bounds_test.cpp`](../../tests/kmd/pipe_bounds_test.cpp)
compiles the header out of the patch
([`scripts/test_kmd_pipe_bounds.py`](../../scripts/test_kmd_pipe_bounds.py),
part of `just ci::win3d-check`) and reads from a pipe of its own, in message
and in byte read mode. The same program built with `-DOLD_DRIVER` runs the
checks on the two read loops the helpers had.

| Build | Checks passed | Checks failed |
| --- | --- | --- |
| The read loops before the patch (`-DOLD_DRIVER`) | 6 | 20, all of them F9 checks: for both ends the 3000-byte message is written past the buffer, the string has no end, and no message of 1 to 4096 bytes is refused |
| The header of the patch | 33 | 0 |

The patched build has 7 checks more. A message above 4096 bytes is one of
them: the old server loop does not end on it, because it asks for 0 bytes
again and again.

## Not changed

- The pipe is still made with a null security descriptor and without
  `FILE_FLAG_FIRST_PIPE_INSTANCE`.
- `SetData()` of both pipe classes calls `wcsncpy_s` with a count equal to
  the buffer length for a text of 1024 units or more. The helpers only pass
  it their own short commands.
- Three other places of the driver use the result of a pool allocation with
  no test: `viogpu_allocation.cpp` (the `GPU_MEM_ENTRY` array of the backing
  attach), `viogpu_queue.cpp` (`VioGpuBuf::Init` zeroes the buffer before it
  tests it) and `viogpu_vidpn.cpp` (`VioGpuObj` of the frame buffer
  segment). `VioGpuBuf::GetBuf` asserts and then writes. The `noexcept` of
  this card does not help there: they are arrays of plain data or are used
  with no test at all.
