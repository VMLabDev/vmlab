# C757. The helpers' pipe read past its buffer, and CreateAllocation used a failed allocation

Findings F9 and F10 of the win3d driver review
([the review](../../../../docs/reviews/win3d-driver.md), card #741). Two
patches of the kernel driver series fix them:
[`kmd-read-helper-pipe-message-inside-buffer.patch`](../../patches/kmd/kmd-read-helper-pipe-message-inside-buffer.patch)
and
[`kmd-check-create-allocation-memory.patch`](../../patches/kmd/kmd-check-create-allocation-memory.patch).
The driver with both is `100.6.101.58120`.

## F9. The pipe of the two helpers

`vgpusrv.exe`, the service, and `viogpuap.exe`, which the service starts in
the console session, talk over the named pipe `viogpupipe<session>`. Each
keeps a buffer of 1024 `wchar_t`, 2048 bytes.

| | Before | After |
| --- | --- | --- |
| `PipeServer::Read` | Asked `ReadFile` for `DATA_BUFFER_SIZE * sizeof(wchar_t)` bytes. `DATA_BUFFER_SIZE` had no parentheses, so that is 1024 × 2 × 2 = 4096 bytes into 2048 | Both ends read through `VioGpuPipeReadMessage` (`viogpu/shared/pipe_bounds.h`), which counts in bytes and never asks for more than the room left |
| `PipeClient::Read` | Asked for 2048 bytes at `&m_buffer[read]`, where `read` counts bytes and the index counts `wchar_t`: the second piece of a message lands at twice its offset | The same function |
| The string | Neither loop wrote a terminator. A sender ends its text with one byte, half a `wchar_t`. `GetData()` read on until it met a zero | The last `wchar_t` of the buffer stays free and the buffer is zeroed behind the message |
| A message that does not fit | Written past the buffer | Taken off the pipe and dropped. The buffer is then an empty string, which the helpers ignore. The next message is read from its first byte |
| `DATA_BUFFER_SIZE` | `DATA_BUFFER_LENGTH * sizeof(wchar_t)` | In parentheses |

The review's claim for the service is confirmed. Its claim for
`viogpuap.exe` holds only for a handle in message read mode, and
`viogpuap.exe` leaves its handle in byte read mode, where `ReadFile` never
reports a second piece. What `viogpuap.exe` did have is the string without
an end.

### Proof in a guest

[`probes/pipe`](../../probes/README.md#the-pipe-probe) is one program linked
with `viogpu/shared/pipe.cpp` of the driver source, once without the patch
(`pipe_probe_before.exe`) and once with it (`pipe_probe_after.exe`). It
drives the two classes of the helpers on a pipe of its own, with the object's
buffer in front of two guard pages, so it counts what is written past the
buffer. [`tests/kmd/pipe-probe.sh`](../../tests/kmd/pipe-probe.sh) runs it as
a new local account that is a member of Users only.

The runs were on helios on 2026-11-24, in a clone of the Windows 11
`26100.1742.11#win3d` template on vmlab-hv. The lab had no `gpu {}` block:
the probe is all user mode and uses no host GPU.

| Case | Source before the patch | Source with the patch |
| --- | --- | --- |
| `server-command`: the server reads `\CONNECTED` into a buffer that held other data | The string runs through the whole buffer and the guard: 5119 units | `\CONNECTED`, 10 units |
| `server-long`: one message of 3000 bytes to the server, then a command | **952 bytes written past the buffer**, from its first byte on. The command behind it is not read right | Nothing past the buffer, the message is dropped, the command is read |
| `server-full`: a message of 2048 bytes with no zero | The string runs past the buffer | Dropped, the next command is read |
| `service-thread`: `Init()` as the service calls it, the thread reads 3000 bytes into the heap buffer | **The process dies**: exit code 116, the low byte of `0xC0000374` (`STATUS_HEAP_CORRUPTION`). The record on disk stays at `requesting` | `HeapValidate` says the heap is whole |
| `client-command`: the client reads `\CLOSE` | The string runs past the buffer | `\CLOSE`, 6 units |
| `client-long`: 3000 bytes to the client in byte read mode | 2048 bytes fill the buffer, the string runs past it | 2046 bytes, 1023 units, terminated |
| `client-long-message-mode`: the same in message read mode | **952 bytes written past the buffer**, the first of them 2048 bytes behind its end | Nothing past the buffer |
| Result | **fails**: 7 of 7 | **passes**: 7 of 7 |

The two programs differ only in `pipe.cpp`, `pipe.h` and the new header.
Their sha256 are `21e79c25…` (before) and `a5751f84…` (after).

### Who can write to the pipe

The review left open who may write to the pipe of the service. The case
`access` of the probe tried to open `\\.\pipe\viogpupipe1` as the standard
user, in the guest with the service of the installed package running:

| Open for | Result |
| --- | --- |
| Reading and writing | Error 5, access denied |
| Reading | Succeeded when no `viogpuap.exe` was connected (this lab has no GPU device). The second try got error 231, all pipe instances busy |

So a standard user cannot send the service a message through its own pipe.
The overflow in the service was reachable by an administrator, and by a
standard user only where the user's process made the pipe name first, which
was not tried. That a standard user can take the one instance of the pipe by
opening it for reading is a separate fault that this card does not change.

### Proof on the build host

[`tests/kmd/pipe_bounds_test.cpp`](../../tests/kmd/pipe_bounds_test.cpp)
compiles the header out of the patch
([`scripts/test_kmd_pipe_bounds.py`](../../scripts/test_kmd_pipe_bounds.py),
part of `just ci::win3d-check`) and reads from a pipe of its own, in message
and in byte read mode. The same program built with `-DOLD_DRIVER` runs the
checks on the two read loops the helpers had.

| Build | Checks passed | Checks failed |
| --- | --- | --- |
| The read loops before the patch (`-DOLD_DRIVER`) | 6 | 20, all of them F9 checks: for both ends the 3000-byte message is written past the buffer, the string has no end, and no message of 1 to 4096 bytes is refused |
| The header of the patch | 33 | 0 |

The patched build has 7 checks more. A message above 4096 bytes is one of
them: the old server loop does not end on it, because it asks for 0 bytes
again and again.

## F10. A failed allocation in CreateAllocation

`DxgkCreateAllocation` made its allocation object with
`new (NonPagedPoolNx) VioGpuAllocation(...)` and called `IsValid()` on the
result with no test. The `operator new` of the driver returns NULL when the
pool has no memory.

| | Before | After |
| --- | --- | --- |
| The result of `new` in `DxgkCreateAllocation` | Used with no test | NULL returns `STATUS_INSUFFICIENT_RESOURCES` |
| The pool `operator new` and `operator new[]` (`viogpu/common/baseobj.h`) | Not `noexcept`: the compiler may take the result for a valid pointer | `noexcept`: the compiler tests the result before it runs a constructor |
| `NumAllocations` | Only `pAllocationInfo[0]` was filled, whatever the count | A count other than 1, or no `pAllocationInfo`, returns `STATUS_INVALID_PARAMETER` |

### A finding of the card: the constructor ran before any test

A NULL check in `DxgkCreateAllocation` alone would not have been a fix. The
driver is built with clang, and for an `operator new` that is not `noexcept`
clang calls the constructor first and tests the pointer afterwards. A small
function with the same shape, compiled with the compiler and the flags of
the driver build (`clang --driver-mode=cl /kernel /O2`), shows it:

| `operator new` declared | Order in the compiled function |
| --- | --- |
| as before the patch | call `operator new`, **call the constructor**, test the pointer |
| `noexcept` | call `operator new`, test the pointer, call the constructor |

So the old driver wrote the members of the object at address 0 inside the
constructor, before it reached `IsValid()`. The same held for the other
objects the driver makes with `new` and tests afterwards, the device, the
device allocation and the command among them. The `noexcept` puts the test
in front of the constructor at each of them.

### Proof in a guest

[`probes/alloc`](../../probes/README.md#the-allocation-probe) opens the
virtio-gpu adapter, makes a device and calls `D3DKMTCreateAllocation` for a
64 by 64 texture in guest memory.
[`tests/kmd/alloc-probe.sh`](../../tests/kmd/alloc-probe.sh) runs it as a new
local account that is a member of Users only, and records a bugcheck of the
guest.

For the failed allocation the script turns on Driver Verifier for
`viogpu3d.sys` with the randomized low resources simulation:
`verifier /flags 0x4 /faults 10000 * alloc_probe.exe 2 /driver viogpu3d.sys`.
That fails every pool allocation the driver makes in the process
`alloc_probe.exe`, with any pool tag, from 2 minutes after the boot. The
probe starts right after the boot, makes its device while allocations still
succeed, and then creates and destroys one allocation again and again (case
`starve`).

One lab for both runs, on helios on 2026-11-24: a clone of the Windows 11
`26100.1742.11#win3d` template with 8 GiB of memory on AMD1
(`0000:72:00.0`), vmlab-hv through the bundle launcher, Venus. "Before" is
the driver of the variant, `100.6.101.58116`, which has none of this card's
patches. "After" is the package of this card installed over it in the same
VM with `scripts/install-into-vm.sh`, driver `100.6.101.58120`.

| Case | Before (58116) | After (58120) |
| --- | --- | --- |
| `one`, `one-v1`: one allocation | Created and destroyed | The same |
| `starve`: allocations until the pool allocation fails | 602 calls succeed, then **bugcheck `0x3B`** (`0xC0000005`): the call did not return | 665 calls succeed, then 200 calls fail, **every one with `0xC000009A`** (`STATUS_INSUFFICIENT_RESOURCES`). No bugcheck |
| `two`, `two-v1`: `NumAllocations = 2` with a resource | `0xC000000D`, no allocation | The same |
| `none`: `NumAllocations = 0` with a resource | `0xC000000D` | The same |
| Result | **fails**: the guest bugchecks on `starve` | **passes**: 6 of 6, no bugcheck |

The record of `starve` before the fix:

```
The computer has rebooted from a bugcheck. The bugcheck was: 0x0000003b
(0x00000000c0000005, 0xfffff801d5d14a02, 0xffffad0633b5e0c0,
0x0000000000000000). A dump was saved in: C:\WINDOWS\MEMORY.DMP.
```

`0x3B` is `SYSTEM_SERVICE_EXCEPTION`: an access violation in kernel code
that a system call of the probe ran. The probe's record on disk stayed at
`starving` with 602 calls that succeeded and none that failed. The dump was
not read, so the note does not name the faulting function from it: the
order of the compiled code above says it is the constructor.

After the fix Driver Verifier counted 200 pool allocations "failed
deliberately", the number of calls the probe saw fail.

The first try of the before-run injected nothing. Its command gave the pool
tags as an empty argument, which the verifier stores as a tag of two
quotation marks: 3118 calls succeeded in 382 seconds and the verifier
counted no failed allocation. The tag `*` is what means every tag.

### The second half: `NumAllocations`

The review asks for a call with `NumAllocations = 2` to fail or to make both
allocations. It fails on the old driver already, with
`STATUS_INVALID_PARAMETER` and no harm to the guest, with a resource and
without one. The probe cannot tell whether Windows refuses the call before
the driver sees it, or after the old driver left the second entry without a
handle. So this half was no crash, and the proof shows no change of
behaviour for it. The check of the patch is for the case that the driver is
called with such a count: it then refuses before it reads the list.

### Proof on the build host

`DxgkCreateAllocation` does not compile outside the WDK.
[`scripts/test_kmd_create_allocation.py`](../../scripts/test_kmd_create_allocation.py)
(part of `just ci::win3d-check`) reads the patch for the three changes, and
compiles [`tests/kmd/pool_new_test.cpp`](../../tests/kmd/pool_new_test.cpp)
with the declaration of `operator new` that the patch adds, and again with
the one it removes, at `-O0` and `-O2`:

| Declaration | Result |
| --- | --- |
| Before the patch | The constructor runs on the NULL pointer |
| With the patch | The new expression gives NULL and no constructor runs |

This shows the rule with the compiler of the build host (GCC 16 on helios).
The compiler of the driver is the one of the table above.

## End-to-end run

`tests/e2e/run.sh --template windows-11 --host-gpu AMD1` on helios on
2026-11-24, at commit `90892b70`: a fresh clone of the Windows 11
`26100.1742.11` template, the package built from the sources of that commit
and installed by the documented command. The guest ran driver
`100.6.101.58120`.

**PASS: 12 of 12 Done checks**, exit 0, and the 8 extra rows pass too. The
eight render probes of the Done items ran at 53 to 60 fps with a correct
readback. The run held AMD1 for 1084 s. No Xid was logged on the host before
or after any of the five holds of this card: 1291 s for the runs on the old
driver, 351 s for the runs on the new one, 1084 s for this run, and two of
17 s and 395 s that ran no test, because a clone was lost to a stopped
daemon of the card's own test setup.

`just ci::check` ran on helios at the same time for the first five minutes
of that hold, while the guest was in its first boot.

## Not changed

- The pipe is still made with a null security descriptor and without
  `FILE_FLAG_FIRST_PIPE_INSTANCE`.
- `SetData()` of both pipe classes calls `wcsncpy_s` with a count equal to
  the buffer length for a text of 1024 units or more. The helpers only pass
  it their own short commands.
- Three other places of the driver use the result of a pool allocation with
  no test: `viogpu_allocation.cpp` (the `GPU_MEM_ENTRY` array of the backing
  attach), `viogpu_queue.cpp` (`VioGpuBuf::Init` zeroes the buffer before it
  tests it) and `viogpu_vidpn.cpp` (`VioGpuObj` of the frame buffer
  segment). `VioGpuBuf::GetBuf` asserts and then writes. The `noexcept` of
  this card does not help there: they are arrays of plain data or are used
  with no test at all.
