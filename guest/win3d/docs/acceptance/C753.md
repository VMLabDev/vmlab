# C753. The installer's state directory and standard users

Card #753 of the vmlab board. Finding F2 of the
[driver review](../../../../docs/reviews/win3d-driver.md) says that
`C:\ProgramData\vmlab-win3d` can be owned or written by a standard user, and
that two startup tasks run a script from it as SYSTEM. This page says what a
guest showed, what changed in `installer/vmlab-win3d.ps1`, and what the same
guest showed afterwards.

## Result

| Code | Check | Installer of `next` | Installer of this card |
| --- | --- | --- | --- |
| P1 | Route 1. The user makes the directory, an administrator installs, the user replaces the staged script, the guest restarts. | **Fails.** The user's script ran: `C:\win3d-statedir-proof.txt` holds `nt authority\system`. Probe exit 1. | **Refused.** `Install.cmd` exits 3 on the user's directory and changes nothing. After the administrator deletes the directory, the install passes and all three attempts of the user are denied. Probe exit 0. |
| P2 | Route 2. A package is installed. The user creates `state.json.tmp`, and one installer run writes the state. | **Fails.** `state.json` then belongs to the user. Probe exit 1. | **Refused.** The user cannot create the file. `state.json` belongs to Administrators. Probe exit 0. |
| P3 | An install by the installer of `next`, then this card's `Install.cmd` over it. | Not applicable. | The inherited access list is replaced. Attempts denied, probe exit 0, and `Uninstall.cmd` ends in `Removed`. |
| P4 | The same, after a user put a file into `bundle\`. | Not applicable. | **Refused**, exit 3, and the file is named. |

Route 3 of the finding (the bundle and its `manifest.json` are in the same
directory) needs route 1 and has no check of its own.

## What the guest showed about the fault

The probe is `tests/installer/statedir-probe.sh`. It makes the standard user
`win3dprobe` and runs every attempt as that user through
`vmlab exec --user`. Before each run it shows that the user is not an
administrator, by group and by token.

The review's statement about `C:\ProgramData` is right. A directory that
SYSTEM makes there gets these entries for `BUILTIN\Users`:
`(A;OICIID;0x1200a9;;;BU)(A;CIID;DCLCRPCR;;;BU)`. The second one lets every
user create files and directories in the directory and in each directory
below it. A directory that the user makes there has the user as its owner
and `(A;ID;FA;;;<user>)`.

Route 1 works as the review says, with one detail. In the user's own
directory, `vmlab-win3d.ps1` is not the user's to write: it has only the
inherited entries. It is the user's to delete, through the full control over
the directory, and then to create again. The first version of the probe used
`Remove-Item -Force`, which clears file attributes first and needs a right
on the file for that, and it was denied. `[IO.File]::Delete` is not.

Route 2 is narrower than the review says. The user can create
`state.json.tmp`, and the installer of `next` writes into that file and
renames it, so `state.json` has the user as its owner. But the next write of
the state makes a new file, and the user loses it again. The repair task
writes the state several times at each boot. So after a restart `state.json`
belonged to SYSTEM (first run of the probe, exit 0, which was not the
expected result). The user owns `state.json` in two cases:

- After a run that writes the state exactly once. Every failed run does
  that: it records `last_error` and stops. The probe uses one: the staged
  script in `Install` mode, which finds no bundle beside itself.
- Between two writes of one run. The probe does not try to win that race.

In the run of P2 the user owned `state.json` for about four seconds. The
repair task of that boot was still running and then wrote the state again.
This is inferred from two facts: the file's owner and group were SYSTEM
afterwards, which only writes of a startup task give (a write through
`vmlab exec` gives Administrators), and its `updated` time was 3.8 s after
the failed run.

The files that a user of route 2 controls are read as SYSTEM: the repair
task reads an owner and an access list for `System32\d3d12.dll` from
`state.json` at each boot, and applies them when they differ.

## The change

`Protect-StateRoot` in `installer/vmlab-win3d.ps1` runs first in every mode
that changes the machine, before the script reads or writes anything in the
directory.

| It finds | It does |
| --- | --- |
| No directory | Creates it with owner Administrators and a protected access list, in the one call: `O:BAG:BAD:PAI(A;OICI;FA;;;SY)(A;OICI;FA;;;BA)(A;OICI;0x1200a9;;;BU)`. Nothing is inherited from `C:\ProgramData`. |
| A directory whose owner is not Administrators, SYSTEM or TrustedInstaller | Stops. The owner of a directory can always rewrite its access list, so nothing in it can be trusted. |
| A directory of an older package (owner Administrators, inherited access list) | Sets the same owner and access list, which the entries below inherit. Then it walks the whole tree and stops when an entry has another owner than those three, or an access entry that lets anybody else change it, or is a link. Links are not followed. |

The access list goes on before the walk, so that nothing can be added behind
the walk. A stop is exit code 3 (every other failure is 1), with the entries
named on standard error. Until the check has passed, the script writes no
journal line and no state, because both files are in that directory.
`scripts/install-into-vm.sh` exits 1 on exit code 3 and does not wait for
`state.json`.

`Write-Json` also deletes a `state.json.tmp` that is there already before it
writes one.

An owner that is an administrator's own account, and not the group, is
refused too. Windows gives files of an elevated administrator and of SYSTEM
the owner Administrators or SYSTEM, and every entry of an installed
directory had one of the two (58 entries after a fresh install).

## Not covered

- Hard links. A user of an older install could have put a hard link to
  another file into the directory before the upgrade. Its owner is the
  owner of the target, so the walk accepts it. To the author's knowledge
  Windows 11 lets a user make a hard link only to a file the user may
  write. That was not checked on this guest.
- The mutex `Global\vmlab-win3d-setup`. A user can create it first. That
  can delay a run and gives no access to a file.
- The other state the package keeps outside this directory
  (`System32\vmlab-win3d\`), which has the access list of `System32`.
