# C751. The capset escape of the kernel driver

Card #751 fixes findings F1, F3 and F6 of
[`docs/reviews/win3d-driver.md`](../../../../docs/reviews/win3d-driver.md) in
[`patches/kmd/kmd-check-capset-escape.patch`](../../patches/kmd/kmd-check-capset-escape.patch).
The driver with the fix is `100.6.101.58117`.

## What the patch changes

| Finding | Before | After |
| --- | --- | --- |
| F1 | `VIOGPU_GET_CAPS` copied the capset with `memcpy` inside `__try` to an address from the escape data | The range is probed with `ProbeForWrite`, its pages are locked with `MmProbeAndLockPages`, both inside `__try`, and the copy goes through a system mapping. A bad address is `STATUS_ACCESS_VIOLATION` |
| F3 | `m_supportedCapsetIDs & (1ull << CapsetId)`, then `m_capsetInfos[CapsetId]` | An id outside 1 to 63 is `STATUS_INVALID_PARAMETER_1` before the shift and the index |
| F6 | `capset_max_size` of the host stored unchecked, `int resp_size = sizeof(GPU_RESP_CAPSET) + capset_size` | A capset above 1 MiB is not supported. The response size is computed in 64 bits, a refused size copies nothing, and the response buffer is zeroed before the request |

The bounds are in one header, `viogpu/common/viogpu_capset_bounds.h`, that
the adapter and the control queue both use and that has no kernel include.

## A finding of the run: `__try` does not catch the copy

The review says the `__try` around the `memcpy` catches a fault on a bad user
address. In this package it does not. The driver is built with clang, whose
`__try` covers the calls inside it and not a fault of an instruction inside
it. The old driver bugchecked `0x3B` (`0xC0000005` in `viogpu3d.sys`) for an
unmapped user address and for a read-only page, as a standard user.

So `ProbeForWrite` in front of the `memcpy` is not enough: an address in
user space that is not mapped passes the probe and then faults in the copy.
The patch therefore does not touch the user address at all. The two calls
that can raise are inside `__try`, and an exception out of a call is caught:
the cases `unmapped-address` and `read-only-address` below show it.

The other `__try` blocks of the driver that touch user memory directly have
the same fault. The copy of the submit escape in `viogpu_device.cpp` is one.
They are not part of this card.

## Proof in a guest (F1, F3)

[`probes/capset`](../../probes/README.md#the-capset-probe) sends the escape
with hostile arguments, one case per process.
[`tests/kmd/capset-probe.sh`](../../tests/kmd/capset-probe.sh) runs it as a
new local account that is a member of Users only, at medium integrity, and
records a bugcheck of the guest.

The runs were on helios on 2026-11-24: AMD1 (`0000:72:00.0`), vmlab-hv
through the bundle launcher, Venus, one clone of the Windows 11
`26100.1742.11#win3d` template. The clone came with driver
`100.6.101.58116`, the series of `next` without the fix. The package of this
card was then installed over it in the same VM with
`scripts/install-into-vm.sh`. The supported capset ids were `0x16` (1, 2 and
4), so k is 1.

| Case | Driver `58116` (before) | Driver `58117` (after) |
| --- | --- | --- |
| `read` | success, 308 bytes written | success, 308 bytes written |
| `unmapped-address` (`0x10000`) | bugcheck `0x3B` (`0xC0000005`, …) | `0xC0000005`, nothing written |
| `read-only-address` | bugcheck `0x3B` (`0xC0000005`, …) | `0xC0000005`, the page unchanged |
| `kernel-address` (`0xFFFF800000000000`) | bugcheck `0x50` (`0xFFFF800000000000`, `0x2`, …): a write to that address | `0xC0000005` |
| `bad-id` (`0xFFFFFFC1`) | bugcheck `0x50` (`0xFFFFB89603037170`, `0x0`, …): a read far past the array | `0xC00000EF` (`STATUS_INVALID_PARAMETER_1`) |
| `near-id` (`65`) | not run | `0xC00000EF` |
| Result | **fails**: 4 of 5 cases bugcheck the guest | **passes**: 6 of 6, no bugcheck |

Before, the probe's record on disk stayed at `requesting` in each of the four
cases, and Windows logged the bugcheck after the reboot. After, the System
log had no bugcheck event newer than those of the before-run. It held three
of the four: the event of `kernel-address` was read right after its reboot
and was gone from the log after the next bugcheck, 30 seconds later. `near-id`
was left out of the before-run: its index lands inside the adapter object,
and what the old driver does with it is not predictable.

The mapped-kernel-address half of F1 (a write that succeeds) was not run:
it needs a test driver that reports a pool address. The bugcheck `0x50` with
access type write at the address the probe chose shows the same copy.

The first before-run stopped at the recovery screen that Windows shows
after two bugchecks. One click on "Restart my PC" through `vmlab vm click`
let it go on. The script now turns that screen off before the cases.

## Proof on the build host (F3, F6)

F6 needs a host that announces a capset of `0xFFFFFFF0` bytes. vmlab-hv has
no switch for a forged answer, and this card adds none. The proof is a unit
test of the driver code:
[`tests/kmd/capset_bounds_test.cpp`](../../tests/kmd/capset_bounds_test.cpp)
compiles the bounds header out of the patch
([`scripts/test_kmd_capset_bounds.py`](../../scripts/test_kmd_capset_bounds.py),
part of `just ci::win3d-check`) and checks the forged size of the finding,
the wrap of the response size, the copy length against the response buffer
for 13 host sizes and 4 user sizes, and the capset ids. The same program
built with `-DOLD_DRIVER` runs the checks on the expressions the driver had.

| Build | Checks failed |
| --- | --- |
| The expressions before the patch (`-DOLD_DRIVER`) | 11: all five F3 checks and all six F6 checks. With `capset_max_size = 0xFFFFFFF0` the response buffer is 9 bytes for a 25-byte header, and the escape copies 65536 bytes from behind it |
| The header of the patch | 0 |

This proves the arithmetic and the bounds that the driver calls. It does not
prove the driver in a guest against a hostile device: no device model
forged the answer.
