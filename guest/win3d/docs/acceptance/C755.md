# C755. Any process could point the scanout at any resource

Finding F7 of the win3d driver review
([the review](../../../../docs/reviews/win3d-driver.md), card #741). A
program had two ways to change what the screen shows without Windows:

- a `VIOGPU_CMD_PRESENT_FLIP` command in the command stream of
  `D3DKMTRender`. The driver checked its size and format and then sent
  `SET_SCANOUT` and a flush with the resource id of the stream, which it
  compared with nothing;
- the `VIOGPU_RES_SET_SCANOUT_BLOB` escape, for any blob allocation of the
  caller.

[Fix](../../patches/kmd/kmd-scanout-only-for-its-owner.patch):

- `DxgkDdiRender` refuses the flip command with
  `STATUS_PRIVILEGED_INSTRUCTION`. Only `Present` writes that command, into
  a DMA buffer of its own, and no user-mode driver of the package sends it.
- The escape stays, because the user-mode driver shows the frames of a
  fullscreen exclusive application with it
  (`yttrium_venus_escape_publish_display` of Mesa). It is served only for
  the process that made the allocation Windows last set as the source of
  the scanout (`DxgkDdiSetVidPnSourceAddress`: the mode set of the
  fullscreen application names one of its allocations), for an allocation
  that this process made, on scanout 0. Every other caller gets
  `STATUS_ACCESS_DENIED`. When Windows takes the scanout back (the desktop,
  the secure desktop), it sets an allocation of another process, and the
  application is refused from then on.

The review's claim is confirmed: a standard user in session 0 replaced the
sign-in screen of the console with one colour.

## Host test

`scripts/test_kmd_scanout_owner.py` takes the header with both decisions
out of the patch and compiles `tests/kmd/scanout_owner_test.cpp` against
it. Built with `-DOLD_DRIVER` the same program runs on what the driver did
before. `win3d-check` of `just ci::check` runs it.

| Check | Before the patch | With the patch |
| --- | --- | --- |
| The five commands of the user-mode driver pass `Render` | pass | pass |
| The fullscreen application that has the scanout shows its own allocation | pass | pass |
| A flip command in the stream of a program | **accepted** | refused |
| A program shows its own allocation while the desktop has the scanout | **accepted** | refused |
| The application, after Windows took the scanout back | **accepted** | refused |
| A program shows an allocation that another process made (2 checks) | **accepted** | refused |
| A program, while Windows has set no source | **accepted** | refused |
| A new process that got the process id of the application | **accepted** | refused |
| A scanout id that is not 0 (2 checks), and a caller that is no process | **accepted** | refused |

Before: 2 of 12 checks pass. With the patch: 12 of 12.

## Guest proof

`probes/scanout/scanout_probe.c` opens the virtio-gpu adapter, makes a
device with a virgl context, makes one allocation of 1024×768 and clears it
to magenta with three virgl commands. Then it asks for the scanout every
15 ms for 14 seconds, and stops at the first refusal:

- `render-flip`: `D3DKMTRender` with one `VIOGPU_CMD_PRESENT_FLIP` command
  for the resource of its allocation;
- `escape`: `VIOGPU_RES_SET_SCANOUT_BLOB` for its allocation, which is a
  blob in this case.

`tests/kmd/scanout-probe.sh` makes a local user that is a member of Users
only, runs one case per process as that user, and takes a screenshot from
the host (`vmlab vm screenshot`) before, 7 seconds into, and after each
case. It counts the pixels with the probe's colour and the pixels of the
most frequent colour.

One lab for both runs: a clone of `windows-11@26100.1742.11#win3d` on AMD1
(`0000:72:00.0`), vmlab-hv, Venus. "Before" is the driver of the variant,
`100.6.101.58116`, the series without this patch. "After" is the package of
this card installed over it, driver `100.6.101.58118`. The probe ran in
session 0, through the guest agent. Nobody was logged on at the console
(`quser`: "No User exists"), so the screen was the sign-in screen of
Windows, which is on the secure desktop.

| Case | Before (58116) | After (58118) |
| --- | --- | --- |
| `render-flip`: first request | `0x00000000`, accepted | `0xc0000096` `STATUS_PRIVILEGED_INSTRUCTION` |
| `render-flip`: requests accepted | all, 891 to 894 in a run | 0 of 1 |
| `render-flip`: the probe's colour on the screen meanwhile | **100.0 %** | 0.0 % |
| `render-flip`: the screen after the probe ended | **"Display output is not active"** (640×480, the host has no scanout) | the sign-in screen |
| `escape`: first request | `0x00000000`, accepted | `0xc0000022` `STATUS_ACCESS_DENIED` |
| `escape`: requests accepted | all, 826 to 894 in a run | 0 of 1 |
| `escape`: the probe's colour on the screen meanwhile | 0.0 % (see below) | 0.0 % |

Before: 0 of 2 cases pass, in each of four runs of the pair. After: 2 of 2
pass, and the System log has no bugcheck record.

With the old driver the picture of the console came back only when Windows
drew its next frame. Until then the console of the VM showed the probe's
colour, and after the probe had destroyed its resource the text of
vmlab-hv for a guest without a scanout.

The escape of the old driver was accepted every time, and the host took
the probe's blob as the scanout: `vmlab-hv.log` has 7012 lines `GPU flush
export failed: 0x1200` from the four runs of this case, two per request. The
colour did not show, because vmlab-hv cannot export a blob of a virgl
context to its display, and it kept the last frame. In one of the two
runs that began with a live screen, the screen was "Display output is not
active" after this case too. A
blob that vmlab-hv can show is a Venus blob, as the user-mode driver makes
it, and the probe would need the Venus protocol for one. So for the escape
the proof is the status of the request and the host log, not a colour.

## The fullscreen application is still served

`probes/scanout/scanout_owner.c` is a fullscreen Direct3D 9 program
(`Windowed = FALSE`, a flip chain) that clears to the same colour and
presents for 20 seconds. `tests/kmd/scanout-owner.sh` logs a test user on at
the console, runs the program on that desktop and takes eight screenshots
from the host meanwhile. Second lab: a clone of the same variant, first with
its driver `100.6.101.58116`, then with the package of this card.

| Mode | Before (58116) | After (58118) |
| --- | --- | --- |
| Composed by Windows, the default of Windows 11 for a fullscreen program | not run | **pass**: 1199 of 1199 presents, the colour on 100.0 % of the screen |
| Exclusive (`EXCLUSIVE=1`: the compatibility layer `DISABLEDXMAXIMIZEDWINDOWEDMODE`) | fails: 1 present succeeds, then 344 fail with `E_FAIL`. A second run: 1 and 340 | fails the same way: 1 present succeeds, then 345 fail with `E_FAIL` |

In the exclusive mode the colour is on 100.0 % of the screen with both
drivers: Windows sets the mode with an allocation of the program, and the
driver shows it. Every later present fails with both drivers. So this is a
fault that was there before this card, and the check of this card is not
its cause: a trace build of the patched driver (`KMD_TRACE=1`, driver
`100.6.101.59118`) has 257 records of `SetVidPnSourceAddress` in such a run,
two of them for allocations of the program, and no record of a decision of
the escape (event 26). The escape was not reached. The fault needs its own
card.

It follows that the served side of the escape check (the process that has
the scanout shows its own allocation) was not seen in a guest. The host test
covers it. The record of event 26 in a trace build shows each decision with
the three process ids, for the card that repairs the exclusive presents.

With a user logged on, the probe was refused in the same two ways
(`0xc0000022`, `0xc0000096`), and the desktop stayed on the screen.

## Not changed

- The escape still takes the size, the offset, the stride and the format
  from the caller. They describe a part of the caller's own allocation, and
  the host checks them against the size of the blob.
- The other commands of a render stream (`VIOGPU_CMD_TRANSFER_TO_HOST` and
  `VIOGPU_CMD_TRANSFER_FROM_HOST`) still carry a resource id that the driver
  does not compare with the resources of the caller. They do not reach the
  scanout. This needs its own card.
- A fullscreen application that lost the scanout gets
  `STATUS_ACCESS_DENIED` for a frame that it shows with the escape after
  that. The user-mode driver reports that present as failed.
