# C413. Fullscreen device-window styles in `d3d9_device`

[C376](C376.md) draft A3: `d3d9_device` fails four assertions of Wine's
`test_window_style` at `device.c` lines 5179, 5184, 5215 and 5220. The
Windows D3D9 runtime (`d3d9.dll`) makes every one of these window calls.
The Win3D driver makes none, and the same four assertions fail with the
same values on the same Windows build without Win3D. No driver change
follows. The four lines stay a known difference of the Wine
`d3d9_device` row.

## The assertions

All four are in the first case of the test (`i=0`). Both windows are
created hidden with `WS_OVERLAPPEDWINDOW`, and the device is created in
fullscreen at the desktop size. Wine expects the runtime to show the
device window and to make it topmost.

| Line | After | Checked | Expected | Win3D | Without Win3D |
| ---: | --- | --- | --- | --- | --- |
| 5179 | `CreateDevice`, fullscreen | style | `0x14cf0000` | `0x4000000` | `0x4000000` |
| 5184 | `CreateDevice`, fullscreen | extended style | `0x108` | `0` | `0` |
| 5215 | `Reset` to windowed | style | `0x14cf0000` | `0x4cf0000` | `0x4cf0000` |
| 5220 | `Reset` to windowed | extended style | `0x108` | `0x100` | `0x100` |

The missing bits are `WS_VISIBLE` (`0x10000000`) and `WS_EX_TOPMOST`
(`0x8`). At line 5179 the frame styles (`0xcf0000`) are also gone, which
Wine accepts for Windows 10 1809 as long as the window is visible.

## Trace

A copy of Wine's `device.c` was built that runs `test_window_style`
alone. Its window procedure prints each style, position, show and
activation message of both windows, with the modules on the stack of the
call that sent the message. The assertions are unchanged. The Win3D run
used AMD1, vmlab-hv, Venus, the Windows 11 `26100.1742.11#win3d`
template and the package built from the patch series of `next` (x64
user-mode driver SHA-256 `d58fcdae…09ecd8`, miniport
`100.6.101.58116`). The installed driver hash matched the package.

These are the calls on the device window in case `i=0` of the Win3D run.
The caller is the first module on the stack below `user32.dll`. No
stack in either trace file names a Win3D module.

| Test step | Call that reached the window | Caller | State after the step |
| --- | --- | --- | --- |
| `CreateDevice`, fullscreen | `SetWindowLong(GWL_STYLE)`, `0x4cf0000` to `0x4000000` | `d3d9.dll+0x9d7dd` | |
| | `SetWindowPos`, 1024×768, flags `0x34` (no z-order, no activation, frame changed) | `d3d9.dll+0xa05da` | hidden, extended style `0` |
| `Reset` to windowed | `SetWindowLong(GWL_STYLE)`, `0x4000000` to `0x4cf0000` | `d3d9.dll+0x628b3` | hidden, extended style `0x100` |
| `Reset` to fullscreen | the two calls of `CreateDevice` again | `d3d9.dll+0x9d7dd`, `+0xa05da` | |
| | `ShowWindow`, show | `d3d9.dll+0xa0624` | |
| | `SetWindowPos`, topmost, flags `0x13` | `d3d9.dll+0xa0653` | visible, extended style `0x8` |
| `SetForegroundWindow(desktop)` | frame styles restored, window minimised | `d3d9.dll+0x628b3`, `+0xa01e8` | style `0x34cf0000`, extended style `0x108` |

The runtime shows the window and makes it topmost from `d3d9.dll+0xa0624`
and `+0xa0653`, directly after the `SetWindowPos` at `+0xa05da`. It
reaches those two calls in `Reset` and not in `CreateDevice`. At the
start of `CreateDevice` another process owned the foreground window. The
test process became the foreground later in the same call: both windows
received `WM_ACTIVATEAPP` under a call from `d3d9.dll+0x4e048`. At `Reset` the test process owned the foreground.
The condition inside `d3d9.dll` was not disassembled. After the focus
loss the styles are the ones Wine expects (lines 5238 and 5242 pass).

The second traced run of the same session printed the same calls from
the same offsets.

## Without Win3D

The control used the same host, vmlab-hv and Windows build with the
`standard` variant of the template and no `gpu` block. Its display
adapter is the `Red Hat VirtIO GPU DOD controller`, a display-only
driver, so Direct3D 9 runs on Microsoft's software path and no Win3D
file is installed.

| Run | Display driver | Program | Checks | Failed assertions | Lines 5179, 5184, 5215, 5220 |
| --- | --- | --- | ---: | ---: | --- |
| Win3D | Win3D `100.6.101.58116` | `d3d9_device` | 56,034 | 11 | fail, values above |
| Win3D | Win3D `100.6.101.58116` | traced `test_window_style` | 87 | 4 | the only failures |
| Control 1 | Red Hat DOD `100.101.104.28500` | `d3d9_device` | 160,214 | 78 | fail, same values |
| Control 1 | Red Hat DOD `100.101.104.28500` | traced `test_window_style` | 87 | 18 | fail, same values |
| Control 2 | Red Hat DOD `100.101.104.28500` | `d3d9_device` | 160,214 | 78 | fail, same values |
| Control 2 | Red Hat DOD `100.101.104.28500` | traced `test_window_style` | 87 | 18 | fail, same values |

Control 2 is a second clone, started 359 s after its last boot where
control 1 started after 128 s. In `CreateDevice` both controls printed
the same two calls from the same offsets (`d3d9.dll+0x9d7dd`,
`+0xa05da`, flags `0x34`) and no call that shows the window. Lines 5179
and 5184 read the state those two calls leave. Lines 5215 and 5220 read
it again after `Reset` to windowed, which only puts the frame styles
back.

In both controls a shell window of another process
(`Windows.UI.Core.CoreWindow`) held the foreground for the whole
program. `SetForegroundWindow` failed in the test, and the runtime did
not reach the show and topmost calls in `Reset` either. That accounts
for the 14 other failures of the traced program there. No control run
had a session where the test process got the foreground, so the `Reset`
to fullscreen path of the table above was seen with Win3D only.

## Other `d3d9_device` lines

The 11 failures of the Win3D run are the four lines of this card, five
`WM_DISPLAYCHANGE` checks (lines 4248, 4319 and 4410, draft A2),
`device.c:3238` (draft A4) and `device.c:15008`.

Each control failed 78 assertions. [C412](C412.md) counted 78 with Win3D in
a session where another window also held the foreground. The failed
lines and their counts are the same in both runs, with one exception:
Win3D fails `device.c:3238` and the controls fail `device.c:15291`. The
foreground, focus and message failures of that C412 run therefore come
from the session and not from the driver.
