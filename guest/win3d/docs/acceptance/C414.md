# C414. Indexed draw without an index buffer

[C376](C376.md) draft A4 reads `device.c:3238` of Wine's `d3d9_device` as
an indexed draw with a valid index buffer and vertex declaration that
returns `E_FAIL` after `DrawPrimitiveUP` cleared stream 0. That reading is
wrong. Line 3238 checks the draw before it: `DrawIndexedPrimitive` with
**no** index buffer set (`SetIndices(NULL)` at line 3234), a valid vertex
declaration and no stream source. Windows expects success there. The draw
with the valid index buffer is checked at line 3245 and passed before this
card. The missing stream is not the cause.
[Fix](../../patches/mesa/d3d9-indexed-draw-without-index-buffer-draws-nothing.patch).

## Trace

Trace builds are the patch series plus a log of the four D3D9 draw entry
points, of every failure return of the draw path, and of `SetStreamSource`
and `SetIndices` calls that set or replace a null buffer. The runs used AMD1
(`0000:72:00.0`), vmlab-hv, Venus and the Windows 11 `26100.1742.11#win3d`
template.

Without the fix the driver saw this, in order:

| Call at the DDI | State at the DDI | Driver result |
| --- | --- | --- |
| `DrawIndexedPrimitive` (checked at line 3238) | no index buffer, index stride 0, stream 0 is the user pointer of the last `DrawPrimitiveUP` with stride 16 | `E_INVALIDARG` from the index size check of `D3D9DrawDiffuse` |
| `SetIndices` (line 3241) | index buffer, stride 2 | `S_OK` |

The runtime forwards an indexed draw that has no index buffer to the
driver, and it returned `0x80004005` to the application for the driver's
`E_INVALIDARG`. That is the only failed draw of the whole program. No
`E_FAIL` return of the draw path and no backend draw failure was hit.

The runtime does not tell the driver that `DrawPrimitiveUP` cleared stream
0. No `SetStreamSource` with a null buffer follows the call. The driver's
stream 0 stays the user pointer.

The fix returns `S_OK` from `DrawIndexedPrimitive` without drawing when no
index buffer is set. With the fix and the trace the driver saw:

| Call at the DDI | State at the DDI | Driver result |
| --- | --- | --- |
| `DrawIndexedPrimitive` (checked at line 3238) | no index buffer | `S_OK`, nothing drawn |
| `SetIndices` (line 3241) | index buffer, stride 2 | `S_OK` |
| `DrawIndexedPrimitive` (checked at line 3245) | index buffer, stream 0 is the user pointer with stride 16 | `S_OK` |
| `DrawIndexedPrimitive` twice (`DrawIndexedPrimitiveUP` at lines 3263 and 3281) | user indices, user vertices | `S_OK` |

The invalid-call cases before it (lines 3166, 3176, 3190, 3197 and 3201)
are made with a null vertex declaration, and the application gets
`D3DERR_INVALIDCALL` for each. The driver failed no draw for them in the
trace. They passed before and pass now.

## Open

- The draw checked at line 3245 reads its vertices through the user pointer of the
  earlier `DrawPrimitiveUP`, because the runtime leaves it in the driver's
  stream 0. The test's vertices are a static array. An application that
  frees the memory between the two draws would make the driver read freed
  memory. Whether the driver should drop the user pointer after each
  `DrawPrimitiveUP` depends on whether the runtime sends it again for every
  such call. That was not measured and is not changed here.
- Since the reboot of helios on 2026-11-22 the AMD1 render node is
  `/dev/dri/renderD129`, not `renderD130`. `renderD128` is the display GPU
  and Nvidia2 has no node while it is passed through. The runs found AMD1
  by its PCI address and refused `renderD128`.

The Wine output, the failure logs and the trace files are on helios under
`/home/vmlab/src/stc/card-414-work`: `run-trace` (run 1), `run-trace2`
(run 2), `run-fix` (runs 3 and 4), `run-ctl` (run 5) and `run-ctl2` (runs 6
and 7).
