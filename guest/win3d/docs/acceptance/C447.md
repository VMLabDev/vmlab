# C447. A desktop that answers late and sound that crackles

Card #447 of the vmlab board. The operator tested the win3d test build of
[operator-test.md](../operator-test.md) in a lab of their own account on
helios (windows-11 `#win3d`, `host_gpu = "Nvidia2"`, `audio = true`) and
reported: "Sound mostly works but crackles a little. There is a performance
issue in vm though. Ui is not responsive. Youtube video plays back ok
though". This page says what was found, what changed, and what the two new
checks of the [adapter suite](../acceptance.md#adapter-suite), `latency` and
`audio`, measured.

## What was wrong in the operator's lab

| Code | Finding | State |
| --- | --- | --- |
| F1 | The VM ran a render server that was not the bundle's. The operator's host config had `qemu_env = { RENDER_SERVER_EXEC_PATH: ... }` on the host GPU, written for QEMU, and vmlab passed it to vmlab-hv, where it wins over the bundle's launcher. This is the cause of [C325](C325.md) again: about 40 frames per second on NVIDIA. | Fixed in vmlab: a host GPU's `qemu_env` no longer reaches vmlab-hv, and `vmlab validate`, `vmlab up` and the start warn (below). |
| F2 | The host was loaded while they tested: load average 42 on 32 CPUs. | Not a defect of vmlab. The two checks now measure what such a load costs. |
| F3 | The viewer could not import the VM's frames, because the VM rendered on the second RTX 5090 and the desktop is on the first, and fell back to shared memory. | Cost and cheaper paths: "The viewer across two GPUs" below. |
| F4 | vmlab-hv's sound path wrote nothing to the VM's log when it ran out of sound. | Fixed: it counts underruns and late callbacks and writes them to `vmlab-hv.log`. |

### The render server (F1)

With the change, a vmlab-hv VM gets the Vulkan environment vmlab derives for
its host GPU and nothing from that GPU's `qemu_binary` or `qemu_env`. Run on
helios with the release build of the branch and a host config that has the
operator's `qemu_env` on `AMD1`:

```text
$ vmlab validate
WARNING: host GPU `AMD1`: qemu_env (RENDER_SERVER_EXEC_PATH, VKR_DEBUG) is QEMU's and does not apply on vmlab-hv; ignored; the VM runs the render server of its vmlab-hv bundle
$ RENDER_SERVER_EXEC_PATH=/usr/lib/virgl_render_server vmlab validate
WARNING: vmlab-hv starts the Venus render server /usr/lib/virgl_render_server from RENDER_SERVER_EXEC_PATH in the environment, not its bundle's <bundle>/libexec/virgl_render_server; an older or unpatched render server costs frame rate (about 40 frames a second on NVIDIA) — unset RENDER_SERVER_EXEC_PATH unless you mean to test another server
```

A third warning names a `vmlab_hv` that is not a bundle's `bin/vmlab-hv`
launcher, the case of C325. A render server can still be forced for a test:
set `RENDER_SERVER_EXEC_PATH` in the environment the supervisor starts in.
vmlab warns and the launcher keeps it.

## The two checks

`latency` and `audio` are rows U1 and S1 of the
[adapter suite](../acceptance.md#adapter-suite). Both take
`ADAPTER_HOST_LOAD`, the number of busy processes the check starts on the
host while it measures.

- `latency`: the time from a pointer event on the console's RFB socket to
  the console frame in which a window has drawn its answer
  (`tests/e2e/adapter/latency.py`, `tests/e2e/adapter/probes/latency_probe.cpp`).
  It waits for the frame with incremental update requests. A first version
  asked for the window's pixels again and again, about 100 times a second:
  the console then held the guest's frames for its copies, the desktop stopped
  changing, and no move was answered in 2 s. A viewer that reads frames
  through the CPU faster than the guest shows them has the same effect.
- `audio`: a 997 Hz sine played for 60 s by a WASAPI shared-mode stream,
  captured from the VM's own PipeWire node, with the discontinuities and
  silent gaps counted (`tests/e2e/adapter/audio.py`,
  `tests/e2e/adapter/probes/tone_probe.cpp`). The row also has what vmlab-hv
  counted and how often the guest's player woke late.

## Measurements

All on helios (32 CPUs), as the account vmlab, vmlab and the vmlab-hv bundle
built from the branch of the card. The host was never idle: other cards built
and tested at the same time, and the load average is given with each run. The
PipeWire of the account vmlab has no real-time scheduling (its threads run at
nice -12) and plays into a dummy output.

## The viewer across two GPUs (F3)

The viewer of the operator printed "dma-buf import/presentation failed;
requesting shared memory: no compatible Vulkan memory type". The viewer
makes its Vulkan device on the GPU that shows the desktop. A frame of a VM
that renders on another GPU is a dma-buf of that other GPU, and the viewer's
device has no memory type it can import it into. The viewer then asks
vmlab-hv for a CPU copy (`CpuCopy` in the frame protocol), and for every
frame after that:

1. vmlab-hv's renderer reads the whole frame back from the render GPU into
   memory, and writes it into a shared-memory ring.
2. The viewer uploads the frame to its own GPU and presents it.

What step 1 costs is measured in the hypervisor's display notes
(`hv/docs/display-export.md` at the root of the vmlab repository, "Flush-to-client
latency"): from the guest's flush to the frame at the client, the median is
0.3 to 1.7 ms for a dma-buf and 21 to 22 ms for a shared-memory client, on
the Radeon and on an RTX 5090 alike. So the fallback adds about 20 ms to
every frame, more than one refresh at 60 Hz, before the viewer's upload.
The `latency` check reads the console through the same CPU copy, and its
`readback_ms` is that copy for one small rectangle of a frame at rest
(table above). The first version of the check showed the second cost: a
reader that asks for copies faster than the guest shows frames holds the
guest's frames, and the desktop stops. The viewer's own part, the upload and
the present, was not measured: the account vmlab has no desktop session on
helios, and no agent may act in the operator's.

Cheaper paths, none of them built:

| Code | Path | What it needs |
| --- | --- | --- |
| O1 | Put the VM on the GPU the desktop is on (`host_gpu`). The viewer then imports the dma-buf and nothing is copied. | Nothing in vmlab. On helios the display GPU is kept away from the agents, so this is the operator's choice. |
| O2 | The viewer makes its Vulkan device on the GPU the VM renders on, imports the frame there without a copy, and presents from that GPU. The compositor then moves the picture between the GPUs, once and not in the VM's render thread. | The frame protocol must name the render device (its DRM device number), and the viewer must pick the Vulkan device by it. Whether KWin on two NVIDIA cards moves such a buffer GPU to GPU or through the CPU is not known and must be measured. |
| O3 | Keep the CPU copy and make it cheaper: copy only the damaged rectangles, and read back without blocking the renderer for the whole copy. | Changes in vmlab-hv's export and in the viewer's upload. It lowers the 20 ms and does not remove it. |

O2 is the path that can bring the two-GPU case near the one-GPU case. It
is not part of this card.
