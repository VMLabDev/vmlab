# C447. A desktop that answers late and sound that crackles

Card #447 of the vmlab board. The operator tested the win3d test build of
[operator-test.md](../operator-test.md) in a lab of their own account on
helios (windows-11 `#win3d`, `host_gpu = "Nvidia2"`, `audio = true`) and
reported: "Sound mostly works but crackles a little. There is a performance
issue in vm though. Ui is not responsive. Youtube video plays back ok
though". This page says what was found, what changed, and what the two new
checks of the [adapter suite](../acceptance.md#adapter-suite), `latency` and
`audio`, measured.

## What was wrong in the operator's lab

| Code | Finding | State |
| --- | --- | --- |
| F1 | The VM ran a render server that was not the bundle's. The operator's host config had `qemu_env = { RENDER_SERVER_EXEC_PATH: ... }` on the host GPU, written for QEMU, and vmlab passed it to vmlab-hv, where it wins over the bundle's launcher. This is the cause of [C325](C325.md) again: about 40 frames per second on NVIDIA. | Fixed in vmlab: a host GPU's `qemu_env` no longer reaches vmlab-hv, and `vmlab validate`, `vmlab up` and the start warn (below). |
| F2 | The host was loaded while they tested: load average 42 on 32 CPUs. | Not a defect of vmlab. The two checks now measure what such a load costs. |
| F3 | The viewer could not import the VM's frames, because the VM rendered on the second RTX 5090 and the desktop is on the first, and fell back to shared memory. | Cost and cheaper paths: "The viewer across two GPUs" below. |
| F4 | vmlab-hv's sound path wrote nothing to the VM's log when it ran out of sound. | Fixed: it counts underruns and late callbacks and writes them to `vmlab-hv.log`. |

### The render server (F1)

With the change, a vmlab-hv VM gets the Vulkan environment vmlab derives for
its host GPU and nothing from that GPU's `qemu_binary` or `qemu_env`. Run on
helios with the release build of the branch and a host config that has the
operator's `qemu_env` on `AMD1`:

```text
$ vmlab validate
WARNING: host GPU `AMD1`: qemu_env (RENDER_SERVER_EXEC_PATH, VKR_DEBUG) is QEMU's and does not apply on vmlab-hv; ignored; the VM runs the render server of its vmlab-hv bundle
$ RENDER_SERVER_EXEC_PATH=/usr/lib/virgl_render_server vmlab validate
WARNING: vmlab-hv starts the Venus render server /usr/lib/virgl_render_server from RENDER_SERVER_EXEC_PATH in the environment, not its bundle's <bundle>/libexec/virgl_render_server; an older or unpatched render server costs frame rate (about 40 frames a second on NVIDIA) — unset RENDER_SERVER_EXEC_PATH unless you mean to test another server
```

A third warning names a `vmlab_hv` that is not a bundle's `bin/vmlab-hv`
launcher, the case of C325. A render server can still be forced for a test:
set `RENDER_SERVER_EXEC_PATH` in the environment the supervisor starts in.
vmlab warns and the launcher keeps it.

## The two checks

`latency` and `audio` are rows U1 and S1 of the
[adapter suite](../acceptance.md#adapter-suite). Both take
`ADAPTER_HOST_LOAD`, the number of busy processes the check starts on the
host while it measures.

- `latency`: the time from a pointer event on the console's RFB socket to
  the console frame in which a window has drawn its answer
  (`tests/e2e/adapter/latency.py`, `tests/e2e/adapter/probes/latency_probe.cpp`).
  It waits for the frame with incremental update requests. A first version
  asked for the window's pixels again and again, about 100 times a second:
  the console then held the guest's frames for its copies, the desktop stopped
  changing, and no move was answered in 2 s. A viewer that reads frames
  through the CPU faster than the guest shows them has the same effect.
- `audio`: a 997 Hz sine played for 60 s by a WASAPI shared-mode stream,
  captured from the VM's own PipeWire node, with the discontinuities and
  silent gaps counted (`tests/e2e/adapter/audio.py`,
  `tests/e2e/adapter/probes/tone_probe.cpp`). The row also has what vmlab-hv
  counted and how often the guest's player woke late.

## Measurements

All on helios (32 CPUs) on 2026-11-22, as the account vmlab, in one lab:
windows-11 `#win3d`, 6 CPUs, 12 GiB, `host_gpu = "AMD1"`, `audio = true`, a
1024x768 console. vmlab and the vmlab-hv bundle are release builds of the
branch of the card, except the rows "main", which run the bundle of the
operator test (`main` at 3161c859). The host was never idle: other cards
built and tested at the same time, so each row has the load average at its
start and its end. "Busy" is `ADAPTER_HOST_LOAD`. The PipeWire of the account
vmlab has no real-time priority (its threads run at nice -12) and plays into
a null sink.

### Latency

120 pointer moves a row. Times are from the pointer event on the RFB socket
to the console frame with the answer, in milliseconds. Every move was
answered in every row.

- With CPUs to spare the desktop answers in 20 ms at the median and 31 ms at
  the 90th percentile: one to two refreshes of the 60 Hz display.
- 16 busy processes on 32 CPUs change nothing. 48 busy processes, more than
  the host has CPUs, as in the operator's test (load average 42), double the
  median and take the 90th percentile to about 70 ms and the worst move to
  100 ms. That is a desktop that feels slow, and it is the host's load, not
  the driver.
- The old render server makes no difference on the Radeon (present rate
  60.21 frames per second against 60.03 and 60.23 with the bundle's). Its
  cost is on NVIDIA, where each Venus fence wakes late ([C325](C325.md): 40
  to 48 frames per second against 58 to 60). That could not be measured
  here: `Nvidia2` was the operator's during this card.
- The console's copy of a frame for the RFB client (`readback_ms`) took 0.7
  to 0.9 ms without added load and 4 to 5 ms with 48 busy processes.

### Sound

One 60 s tone a row. `audio.py` sorts the breaks by the jump of the sine's
phase across them. A stretch of 480 frames whose two ends cancel, and a
shift by whole 10 ms periods, are sound from one or two periods earlier: the
guest refilled a period after the sound card model had read it. A silent
gap of whole 256-frame quanta is the host half: the sound server had no
buffer in time. A shift by whole quanta is frames lost in the sound server
or in the capture.

| vmlab-hv | Busy | Load average | Breaks | Late guest periods (stretches + shifts) | Silent gaps | Quantum shifts, other | Queue underruns, late callbacks (vmlab-hv log) | Late wakes of the guest's player |
| --- | ---: | --- | ---: | --- | --- | --- | --- | ---: |
| main | 0 | 70 to 16 | 2 | 0 | 0 | 2, 0 | main logs neither | 0 |
| branch, last build | 0 | 8.6 to 4.3 | 3 | 0 | 0 | 1, 2 | 0, 0 | 0 |

| branch, last build | 16 | 4.3 to 20.9 | 9 | 0 + 1 | 2 (32 ms) | 4, 0 | 0, 2 (longest 26 ms) | 1 |

### Why it crackles

| Code | Cause | Evidence | State |
| --- | --- | --- | --- |
| K1 | The guest refills a period late and the sound card model plays the old one. The HDA model reads the guest's cyclic buffer on the host's clock. Windows writes each 10 ms period a short time before it is read. When a vCPU loses the CPU for longer than that, the model reads the period that was there one or two periods (20 ms of buffer) earlier. | Under 48 busy processes about 100 of 110 to 119 breaks are stretches of exactly 480 frames or shifts by whole periods, the guest's player woke up to 39 ms late, and vmlab-hv's queue never ran empty. With CPUs to spare there are none. | Not fixed. vmlab-hv cannot see this in its queue, so its counters stay at zero. "What is left" below. One source that needs no host load is fixed by card #912: a virtio-gpu context create kept a vCPU out of the guest for 5 to 17 ms ([C912](C912.md)). |
| K2 | The PipeWire callback of vmlab-hv comes late and the sound server plays a silent quantum. vmlab-hv asks for a 256-frame quantum (5.3 ms) and fills it on an ordinary thread. | Silent gaps of 5.3 ms and multiples, together with "late callbacks" in the VM's log: 5 gaps with 4 late callbacks, 2 with 2. | Counted and logged now. Not fixed. Moving the callback to PipeWire's data thread (`RT_PROCESS`) was tried on this account, where that thread has no real-time priority: 22 silent gaps in 60 s against 1 to 5. It is not used. |
| K3 | vmlab-hv's own queue runs empty. | Never seen: 0 underruns in every run. | The queue now holds two host callbacks at least and grows by 256 frames after an underrun, up to 2048 frames. No run needed it. |
| K4 | Two to three breaks a minute with CPUs to spare are shifts by whole host quanta. | The same with the bundle of main. | Frames lost in the PipeWire of the account vmlab or in `pw-record`, which have no real-time priority there. Not the VM's. A session with real-time priority (rtkit) was not available to an agent. Located by card #912: `pw-record` loses them when its write to the capture file waits for the disk, and the check now captures to tmpfs ([C912](C912.md)). |

The change of this card does not lower the number of breaks. It names them:
the VM's log now has a line for every 10 s with an underrun or a late
callback, and the check tells a late guest from a late host.

### What is left

For a follow-up card. The check is `tests/e2e/adapter.sh <lab> win <dir>
audio` with `ADAPTER_HOST_LOAD=48`, and it is done when the row has no late
guest period under that load.

| Code | Work | Notes |
| --- | --- | --- |
| A1 | For K1: the HDA model must not fetch a period the guest has not refilled. | Signs it can use: the IOC of the period before is not acknowledged yet, and the bytes are the same as the last time this part of the buffer was read. It then holds the DMA and the link position, plays from the host queue, and catches up afterwards with the deferred frame time it already keeps. The queue of this card can hold up to 2048 frames for it. Limits: a guest that loops one buffer on purpose has the same bytes each lap, silence has too, a hold must end after a bounded time, and the snapshot layout of the model must stay. The Windows driver's cyclic buffer was 960 frames, so a fetch that only runs later than the link position buys less than 10 ms. |
| A2 | For K2: ask the sound server for a larger quantum after late callbacks. | vmlab-hv asks for 256 frames. 1024 frames would have covered every late callback measured here (the longest was 26 ms). It adds that much latency, so it should grow only when callbacks come late. |
| A3 | Measure in a desktop session whose PipeWire has real-time priority, the operator's. | No agent may act there. `RT_PROCESS` should be tried again there, and the two to three breaks a minute of K4 should be gone. |

## The viewer across two GPUs (F3)

The viewer of the operator printed "dma-buf import/presentation failed;
requesting shared memory: no compatible Vulkan memory type". The viewer
makes its Vulkan device on the GPU that shows the desktop. A frame of a VM
that renders on another GPU is a dma-buf of that other GPU, and the viewer's
device has no memory type it can import it into. The viewer then asks
vmlab-hv for a CPU copy (`CpuCopy` in the frame protocol), and for every
frame after that:

1. vmlab-hv's renderer reads the whole frame back from the render GPU into
   memory, and writes it into a shared-memory ring.
2. The viewer uploads the frame to its own GPU and presents it.

What step 1 costs is measured in the hypervisor's display notes
(`hv/docs/display-export.md` at the root of the vmlab repository, "Flush-to-client
latency"): from the guest's flush to the frame at the client, the median is
0.3 to 1.7 ms for a dma-buf and 21 to 22 ms for a shared-memory client, on
the Radeon and on an RTX 5090 alike. So the fallback adds about 20 ms to
every frame, more than one refresh at 60 Hz, before the viewer's upload.
The `latency` check reads the console through the same CPU copy, and its
`readback_ms` is that copy for one small rectangle of a frame at rest
("Latency" above). The first version of the check showed the second cost: a
reader that asks for copies faster than the guest shows frames holds the
guest's frames, and the desktop stops. The viewer's own part, the upload and
the present, was not measured: the account vmlab has no desktop session on
helios, and no agent may act in the operator's.

Cheaper paths, none of them built:

| Code | Path | What it needs |
| --- | --- | --- |
| O1 | Put the VM on the GPU the desktop is on (`host_gpu`). The viewer then imports the dma-buf and nothing is copied. | Nothing in vmlab. On helios the display GPU is kept away from the agents, so this is the operator's choice. |
| O2 | The viewer makes its Vulkan device on the GPU the VM renders on, imports the frame there without a copy, and presents from that GPU. The compositor then moves the picture between the GPUs, once and not in the VM's render thread. | The frame protocol must name the render device (its DRM device number), and the viewer must pick the Vulkan device by it. Whether KWin on two NVIDIA cards moves such a buffer GPU to GPU or through the CPU is not known and must be measured. |
| O3 | Keep the CPU copy and make it cheaper: copy only the damaged rectangles, and read back without blocking the renderer for the whole copy. | Changes in vmlab-hv's export and in the viewer's upload. It lowers the 20 ms and does not remove it. |

O2 is the path that can bring the two-GPU case near the one-GPU case. It
is not part of this card.
