# C754. The scanout count of the host as a loop bound

Card #754 of the vmlab board, finding F5 of the driver review
(the document `win3d-driver.md` in the reviews of the vmlab repository). The
kernel driver read `num_scanouts` from the device configuration and used it
unchecked as the bound of two loops. This page says what the fault did on a
guest, what the fix is, and what the proof measured.
[Fix](../../patches/kmd/kmd-bound-host-scanout-count.patch).

## The fault

| Code | Place in the patched source | Fault |
| --- | --- | --- |
| P1 | `VioGpuVidPN::GetEdids` | Loops to the host's count and copies 256 bytes to `m_EDIDs[i]`. The array has `MAX_CHILDREN` (1) entries, so the copy for scanout 1 lands on the 256 bytes of members after it, among them `m_bEDID`, `m_SystemDisplayInfo`, `m_pFrameBuf`, `m_sourceRes`, the vsync spin lock and the vsync timer. |
| P2 | `CtrlQueue::GetEdidInfo` | Reads 256 bytes at `edid + id * 128` of a 1024-byte field. An id above 6 reads past the response. |
| P3 | `CtrlQueue::GetDisplayInfo` | Reads `pmodes[id]`, an array of 16. An id above 15 reads past the response. |

## The fix

- The adapter clamps the count to `MAX_CHILDREN` where it reads it from the
  device configuration. The driver has one target, so it uses one scanout.
- Both loops also stop at `MAX_CHILDREN`, at the array.
- `GetEdidInfo` and `GetDisplayInfo` refuse an id that their response has no
  room for, and copy nothing.

The series has 16 patches with it, so the default driver version of the
build is `100.6.101.58117`.

## What the true vmlab-hv does

The review took a host with two scanouts and `VIRTIO_GPU_F_EDID` as enough to
reach P1. On vmlab-hv it is not. The driver sends `GET_EDID` when the host
offers the bit, but it never acks the bit. vmlab-hv refuses `GET_EDID` from a
driver that did not ack it, so on vmlab-hv the driver copies no EDID at all
and uses its built-in one. A vmlab-hv changed to report two scanouts and
nothing else started the unfixed driver with no request past scanout 0 (run
R0 below). QEMU answers `GET_EDID` without the ack. The fault is reached by a
host that answers like QEMU, or by a hostile one.

## The forged host

`tests/kmd/hv-forge-scanouts.patch` is a test-only change of vmlab-hv's
virtio-gpu. It is not applied in any build of vmlab. With
`VMLAB_HV_FORGE_SCANOUTS=2` in the environment the device reports two
scanouts in its configuration, enables two modes in the display info, and
answers `GET_EDID` for scanouts 0 and 1 without the ack, as QEMU does. The
device still has one scanout. It writes one line to the VM's `vmlab-hv.log`
for the count and one for each `GET_EDID`. With `VMLAB_HV_FORGE_EDID_FILL=a5`
the EDID field of the answer for scanout 1 holds that byte 1024 times, where
it otherwise holds the EDID of scanout 0.

`tests/kmd/scanout-count-probe.sh` reads those lines for the newest start of
the VM and asks the guest for the display device, its problem code, the
monitors and the bugcheck events of the System log. It passes when the host
reported more than one scanout, the driver asked for the EDID of scanout 0
only, the device has problem code 0, Windows has one monitor, and the System
log has no bugcheck event.

## Runs

On helios on 2026-11-24, AMD1 (`0000:72:00.0`), Windows 11
`26100.1742.11#win3d`, vmlab and the vmlab-hv bundle of vmlab commit
`3161c859`, the forged vmlab-hv built from the same commit with the patch.
Each run is a fresh clone of the variant. The variant has driver
`100.6.101.58116`, which is the series without the fix. For the runs after
the fix, the package of this card was installed on the true vmlab-hv, the VM
was stopped, and it was started again on the forged one.

| Run | Driver | Host | Probe | What happened |
| --- | --- | --- | --- | --- |
| R0 | `58116` | two scanouts, `GET_EDID` refused without the ack (the true vmlab-hv's rule) | pass | No `GET_EDID` was answered. Problem code 0, one monitor. |
| R1 | `58116` | forged, the EDID of scanout 0 for both | **fail** | The host answered `GET_EDID` for scanout 0 and for scanout 1: the driver copied 256 bytes past `m_EDIDs`. Nothing showed it: problem code 0, one monitor, no bugcheck event. |
| R2 | `58116` | forged, scanout 1 filled with `a5` | **fail** | The guest did not start. The host answered both requests twice, 22 s apart, the guest agent never answered, and the VM powered off after 100 s. Started again on the true vmlab-hv, its System log has event 41 of Kernel-Power (restart without a clean shutdown) and "Dump file generation succeded" of volmgr, and `C:\Windows\MEMORY.DMP` was written 28 s after the start of the run. The header of that dump has bugcheck `0x0000001E` (`KMODE_EXCEPTION_NOT_HANDLED`) with exception `0xC0000005`, an access violation, at address `0xFFFFFFFFFFFFFFFF`. |
| R3 | `58117` | forged, the EDID of scanout 0 for both | pass | The host reported 2 scanouts and answered one `GET_EDID`, for scanout 0. Problem code 0, one monitor, no bugcheck event. |

R1 is the case of a QEMU with `max_outputs=2`. It corrupts the VidPN object
and shows nothing, because the second half of a real EDID and the zeros
after it land on members that the driver sets again later or that take those
values. The review expected a crash there. R2 shows the same write with
other bytes: the guest is lost.

## Not measured

- No run used Driver Verifier or special pool. `m_EDIDs` is a member in the
  middle of the VidPN object, so special pool does not catch P1. The host's
  log of the answered request is the evidence that the copy ran.
- No guest run used a count above 2. P2 and P3 need a count above 7 and
  above 16. The clamp to 1 covers them, and their own bounds are by reading.
- The guests of this card ran on vmlab-hv only. No QEMU guest was started.

## The acceptance run

`tests/e2e/run.sh --template windows-11 --host-gpu AMD1` on the true vmlab-hv
with the package of this card (driver `100.6.101.58117`, a fresh lab, the
package installed by the documented command): 12 of 12 Done checks pass,
exit status 0. The host log had no Xid before or after any run of this card.
